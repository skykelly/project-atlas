# I-3. Agent·업무 실행 기술

[주제 목차](README.md) · [모델·비용](I-2_models_cost.md) · [기업 지식·메모리](I-4_knowledge_data_memory.md) · [변경 이력](LOG.md)

조사 범위 **2026-01-01~2026-10-06**, 현행 문서 확인일 **10-06**. 공식 발표·기술 문서·공급자 실험을 비교했다. 아래 도입 패턴은 분석·적용 제안이며 실제 기업 배포 성과가 아니다.

## 1. 답변 생성에서 ‘상태를 가진 과업 실행’으로

Agent는 목표를 받은 뒤 도구를 선택하고 중간 결과를 확인하며 다음 행동을 결정한다. Harness는 이 반복을 운영하는 프로그램이다. 모델이 판단을 잘해도 작업 중 서버가 재시작되거나 인증이 만료되면 업무가 끝나지 않는다. 2026년 공개 제품은 이 실행·상태·복구 기반을 SDK 또는 관리 서비스로 제공하는 방향을 보여 준다.

| 구성 | 맡는 일 | 빠졌을 때의 문제 |
|---|---|---|
| 모델 | 계획·도구 선택·결과 해석 | 잘못된 인자·순서·판단 |
| Harness | 반복·중단·재개·승인·도구 연결 | 실행이 멈추거나 같은 행동 반복 |
| Sandbox | 파일·명령·코드의 격리된 실행 | 자격증명·내부 자원 노출 |
| Session | 사건·상태·history의 보존 | 재시작 때 진행 내용 상실 |
| 업무 시스템 | 최종 기록·수락·부작용 확인 | 완료 발화와 실제 상태 불일치 |

세션이 남는다는 것은 과업 전체가 올바르게 완료된다는 뜻은 아니다. 예를 들어 CRM 업데이트 직후 통신이 끊기면 Agent는 실패로 오인해 같은 기록을 다시 쓸 수 있다. 재개 가능한 런타임에도 업무 식별자·중복 방지·최종 상태 조회가 필요하다.

## 3. SDK·managed runtime·cloud compute 선택

| 선택지 | 서비스가 맡는 부분 | 기업이 맡을 부분 | 주요 조건 |
|---|---|---|---|
| OpenAI Agents SDK | agent loop·도구 호출·sandbox 통합 | 앱 배포·상태 저장·도구·승인 정책 | 고객 앱에서 실행; 4월 GA는 SDK 발표 기준 |
| OpenAI Agents API | harness·sessions·context compaction·복구 | 업무 tool·실행 환경·최종 상태 검증 | 현행 미국 residency만, ZDR 미지원; self-hosted도 예외 아님 |
| Claude Managed Agents | harness·세션·실행 기반 | instructions·tools·환경·업무 완료 정의 | beta; MCP tunnels·dreaming은 제한 preview; ZDR·HIPAA BAA 미대상 |
| AWS AgentCore | framework와 분리된 compute·identity·관측 기반 | 모델·framework·업무 loop와 상태 설계 | microVM과 instances의 지속 시간·가격·리전이 다름 |

Managed를 선택하면 직접 만드는 운영 코드가 줄지만 업무 책임까지 이전되지는 않는다. SDK는 기존 제품 로직과 세밀하게 연결하기 좋고, managed API는 장기간 실행 기반의 구축 부담을 줄이는 후보다. 특정 내부망·데이터 보존 요구가 있다면 먼저 그 요구를 충족하는 옵션을 좁힌 뒤 품질을 비교해야 한다.

AWS의 8시간은 microVM invocation 조건이고 14일은 instances 세션 지속 조건이다. instances 발표 리전에는 서울이 없다. 3월 MCP 지원의 서울 포함 목록을 다른 기능에 적용하면 잘못된 배포 계획이 된다.

## 4. 실행 인터페이스 — 함수·MCP·컴퓨터 사용

| 방식 | 적합한 업무 | 구현·검증 초점 |
|---|---|---|
| 함수/API tool | 구조화된 CRM 조회·재고·승인 등록 | schema·필수 인자·권한·idempotency·응답 상태 |
| MCP | 여러 서비스의 도구·자료 연결 | 서버 신뢰·tool 범위·사용자 identity·진행/입력 처리 |
| Shell·파일 | 자료 분석·코드 변경·문서 생성 | mount·출력 경로·격리·네트워크·비밀정보 경계 |
| Computer use | API가 부족한 웹 업무·화면 작업 | 페이지 접근·인증·UI 변화·행동 후 최종 확인 |

이 표는 구현 선택에 관한 분석이다. API로 안정적으로 처리 가능한 기록 쓰기를 화면 클릭으로 돌리면 성공 판단이 더 복잡해질 수 있다. 반대로 API가 없는 업무에서는 화면 조작이 실제 연결 수단이 된다. 둘의 선택은 데모의 인상보다 완료 검증·유지 비용에 달려 있다.

OpenAI 현행 computer use 문서는 origin·인증 승인 요청을 애플리케이션이 처리하게 한다. 승인 요청 접수는 탐색 성공과 구분된다. 따라서 승인 UI, 중단·재개, 완료 상태 확인은 별도 단계다. [구현 조건](evidence/OAI-AGENTS-20261006-001.md)

## 5. 장시간 실행의 복구·보안 패턴

Anthropic은 harness·sandbox·세션을 분리한 내부 구조 변경 뒤 TTFT p50 약 60%, p95 90% 이상 감소를 보고했다. 필요한 때만 실행 환경을 준비하는 구조의 효과이며, 과업 전체가 같은 비율로 빨라졌다는 의미는 아니다. 절대 지연·표본·독립 재현은 공개되지 않았다. [측정 조건](evidence/ANT-RUNTIME-20261006-001.md)

| 실패 장면 | 보존·확인할 것 | 재개 규칙 제안 |
|---|---|---|
| Sandbox 종료 | 파일 snapshot·artifact 위치·현재 단계 | 새 환경 복원 뒤 산출물 검증 |
| Harness 재시작 | durable events·tool 결과·승인 상태 | 마지막 기록에서 이어서 실행 |
| 쓰기 후 timeout | 요청 ID·외부 record ID·수신 상태 | 상태 조회 뒤 필요할 때만 재시도 |
| 권한 회수·인증 만료 | 현재 사용자·tool scope | 읽기/쓰기 재인증, 기존 허용을 무조건 재사용하지 않음 |
| 맥락 압축 오류 | 원 history·근거·미완료 항목 | 관련 사건 재조회, 요약을 사실 원본으로 대체하지 않음 |

여기서 ‘복구’는 컨테이너만 되살리는 작업보다 넓다. 업무 상태가 이미 바뀌었는지 확인해야 안전하게 이어갈 수 있다. 자격증명을 실행 환경 밖에 두는 구조도 중요하지만, 정당한 권한을 가진 도구의 잘못된 사용까지 자동으로 막지는 않는다.

## 6. 멀티 Agent — 분할 가능한 과업과 검증 가능한 산출물

| 실험 관측 | 확인된 규모 | 읽는 방식 |
|---|---|---|
| 병렬 compiler 개발 | 16개 Agent·약 2주·거의 2,000 세션 | 공급자 연구자의 특정 프로젝트 |
| 사용량·비용 | 입력 20억·출력 1억4,000만 tokens; API 약 $20,000 미만 | 설계·검수 노동 포함 총원가 아님 |
| 산출물 | 약 10만 줄 Rust; Linux 6.9 빌드 | 상용 compiler 대체나 유지보수 품질과 별개 |
| 제한 | 일부 GCC 의존·낮은 최적화 효율 | 시험 통과와 완제품 품질 구분 |

[원문·측정 한계](evidence/ANT-TEAMS-20261006-001.md). 이 실험은 Agent를 많이 투입하면 비례해 빨라진다는 근거가 아니다. 작업 경계·공유 상태·충돌 처리·시험 설계가 있어야 병렬 실행의 이점을 얻는다.

실무 적용에서는 독립적인 문서 묶음 분석이나 서로 다른 검증 항목처럼 분리 가능한 과업부터 비교할 수 있다. 여러 Agent가 동일 파일·동일 고객 기록을 수정하면 병합·책임·중복 실행 비용이 커진다. 단일 Agent 기준선을 두고, 병렬화 뒤 수락된 결과당 비용·시간·충돌을 비교하는 것이 합리적이다.

## 7. 성공·일관성·비용을 함께 평가

| 평가 항목 | 직접 확인할 대상 | 피할 해석 |
|---|---|---|
| 업무 성공 | 실제 DB·artifact·승인 완료 | ‘완료했다’라는 발화만 채점 |
| 부작용 | 다른 기록·권한·데이터 변경 | 목표 결과만 보고 손상을 누락 |
| 반복 일관성 | 동일 과업 다회 trial | 최고 성공 사례를 평균으로 제시 |
| 복구 | timeout·restart·인증 실패 과업 | 정상 경로 성공을 복구 보장으로 사용 |
| 경제성 | tokens·tools·compute·재시도·검수 | 단일 token 가격으로 총원가 추정 |

[Agent eval 원문](evidence/ANT-EVALS-20261006-001.md)은 pass@k와 pass^k를 구분한다. **가상 예시**로 매회 성공률 90%이고 독립이면, 3회 중 한 번 이상 성공은 99.9%, 3회 모두 성공은 72.9%다. 실제로는 실패가 동일 데이터·권한·도구에 상관될 수 있어 이 산식을 그대로 적용할 수 없다.

1. 실제 실패를 포함한 과업과 최종 상태의 정답을 정의한다.
2. 코드 검증으로 상태·부작용을 확인하고 모호한 품질은 전문가 기준을 추가한다.
3. 모델·harness·tool 버전과 반복 횟수를 함께 기록한다.
4. 변경 전후 성공·복구·완료시간·수락당 비용을 비교한다.

## 8. 비교 종합과 적용 우선순위

2026년 원문이 보여 주는 변화는 실행 인프라의 상품화다. 그러나 장기간 실행 가능한 서비스와 책임 있게 업무를 끝내는 시스템은 구분해서 설계해야 한다. 비교의 핵심은 어떤 공급자가 agent loop를 맡는지, 상태가 어디 남는지, 외부 쓰기를 어떻게 확인하는지다.

- **읽기·분석**: 명확한 출처와 검증 가능한 산출물부터 managed/SDK 기준선을 만든다.
- **제한된 쓰기**: 허용 tool·대상·업무 ID·승인·수신 상태를 연결한다.
- **장시간·병렬 작업**: checkpoint·충돌·복구·compute 비용이 추가되는 효과를 측정한다.
- **확장 판단**: 관측된 성공률과 수락당 비용으로 정하고, 데모 시간·Agent 수로 결정하지 않는다.

이는 적용 가설이다. 현재 조사는 공개 원문 확인이며 실제 기업 시스템의 운영 성능은 측정하지 않았다. 지식·권한·메모리 설계는 [I-4](I-4_knowledge_data_memory.md), 과업당 경제성은 [I-2](I-2_models_cost.md)에 연결한다.
