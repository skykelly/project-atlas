# I-3. Agent·업무 실행 기술

[주제 목차](README.md) · [모델·비용](I-2_models_cost.md) · [기업 지식·메모리](I-4_knowledge_data_memory.md) · [변경 이력](LOG.md)

조사 범위 **2026-01-01~2026-10-07**, 기존 조건 확인일 **10-06**, 추가 원문 확인일 **10-07**. 공식 발표·기술 문서·공급자 실험을 비교했다. 아래 도입 패턴은 분석·적용 제안이며 실제 기업 배포 성과가 아니다.

2026년 Agent 경쟁은 모델 호출을 장기 과업의 실행 서비스로 묶는 방향으로 진행한다. 공급자는 세션·도구·복구·평가를 판매하고, 고객은 업무 수락 기준과 외부 변경의 책임을 유지한다. 비용을 줄이는 하네스와 품질을 높이는 하네스가 항상 같지는 않다. 제품 조건·공급자 실험·기업 데이터 연결을 대조해 그 차이를 분석한다.

## 1. Agent는 답변이 끝난 뒤에도 상태를 책임진다

Agent는 도구를 고르고 중간 결과를 확인한 뒤 다음 행동을 결정한다. Harness가 이 반복을 운영한다. 모델이 정확해도 서버 재시작, 인증 만료, 외부 쓰기 실패를 처리하지 못하면 업무는 끝나지 않는다. 2026년 제품은 실행·상태·복구 기반을 SDK와 관리 서비스로 상품화했다.

| 구성 | 맡는 일 | 빠졌을 때의 문제 |
|---|---|---|
| 모델 | 계획·도구 선택·결과 해석 | 잘못된 인자·순서·판단 |
| Harness | 반복·중단·재개·승인·도구 연결 | 실행이 멈추거나 같은 행동 반복 |
| Sandbox | 파일·명령·코드의 격리된 실행 | 자격증명·내부 자원 노출 |
| Session | 사건·상태·history의 보존 | 재시작 때 진행 내용 상실 |
| 업무 시스템 | 최종 기록·수락·부작용 확인 | 완료 발화와 실제 상태 불일치 |

세션 보존은 과업 완료를 보장하지 않는다. CRM 업데이트 직후 통신이 끊기면 Agent가 같은 기록을 다시 쓸 수 있다. 재개 가능한 런타임도 업무 식별자, 중복 방지, 최종 상태 조회를 갖춰야 한다.

## 3. SDK·관리형 런타임·클라우드 연산의 책임선을 긋는다

| 선택지 | 서비스가 맡는 부분 | 기업이 맡을 부분 | 주요 조건 |
|---|---|---|---|
| OpenAI Agents SDK | agent loop·도구 호출·sandbox 통합 | 앱 배포·상태 저장·도구·승인 정책 | 고객 앱에서 실행; 4월 GA는 SDK 발표 기준 |
| OpenAI Agents API | harness·sessions·context compaction·복구 | 업무 tool·실행 환경·최종 상태 검증 | 현행 미국 residency만, ZDR 미지원; self-hosted도 예외 아님 |
| Claude Managed Agents | harness·세션·실행 기반 | instructions·tools·환경·업무 완료 정의 | beta; MCP tunnels·dreaming은 제한 preview; ZDR·HIPAA BAA 미대상 |
| AWS AgentCore | framework와 분리된 compute·identity·관측 기반 | 모델·framework·업무 loop와 상태 설계 | microVM과 instances의 지속 시간·가격·리전이 다름 |

관리형 서비스를 선택하면 운영 코드는 줄어든다. 업무 책임은 기업에 남는다. SDK는 기존 제품 로직과 세밀하게 연결하고, managed API는 장기간 실행 기반의 구축 부담을 낮춘다. 특정 내부망·데이터 보존 요구가 있다면 먼저 그 요구를 충족하는 옵션을 좁힌 뒤 품질을 비교해야 한다.

AWS의 8시간은 microVM invocation 조건이고 14일은 instances 세션 지속 조건이다. instances 발표 리전에는 서울이 없다. 3월 MCP 지원의 서울 포함 목록을 다른 기능에 적용하면 잘못된 배포 계획이 된다.

### 3.1 공급자는 실행 기반을 팔고, 고객은 업무 검증을 계속 맡는다

SDK·관리형 런타임·클라우드 연산은 서로 다른 구매다. SDK를 고르면 기업이 애플리케이션 안에서 모델 호출과 상태를 운영한다. 관리형 런타임을 고르면 공급자가 반복 실행·세션·복구 일부를 제공한다. 클라우드 실행 환경은 그 코드를 돌릴 연산과 격리를 제공한다. 세 상품의 기능이 겹쳐도 최종 업무 결과를 승인하는 주체는 달라지지 않는다.

| 시장에서 상품이 되는 기능 | 공급자가 확보하는 접점 | 기업에 남는 비용·책임 |
|---|---|---|
| 장기 세션·context 관리 | 실행 이력과 호출 경로 | 원 업무의 정답·수락·보존 정책 |
| 도구·identity 연결 | 내부 시스템 접근 경로 | 사용자 권한·쓰기 범위·자격증명 회수 |
| checkpoint·복구 | 반복 실행의 운영 기반 | 이미 발생한 외부 변경의 중복 방지 |
| 평가·관측 | 실패 기록과 품질 개선 경로 | 업무 기준·예외·검수 노동 |
| 모델·하네스 일체화 | 버전·기본 설정·호출 과금 | 공급자 교체 시 재평가·이력 이관 |

이 표는 기존 제품 조건을 연결한 사업 분석이다. 런타임을 구매하면 자체 운영 코드를 줄일 수 있다. 동시에 세션 형식, 도구 호출, 기본 모델과 관측 체계에 대한 의존이 커질 수 있다. 모델 API를 바꾸는 비용과 런타임을 바꾸는 비용을 따로 계산해야 한다. 전자는 답변 품질·토큰·가격을, 후자는 상태·복구·권한·업무 부작용까지 다시 시험한다.

모델이 개선될수록 기존 하네스의 우회 코드가 불필요해질 가능성도 있다. 반대로 고객의 실패 기록을 더 많이 축적한 런타임은 재시도·복구·평가에서 우위를 유지할 수 있다. 시장의 지속적인 수익 기회는 이런 운영 부담을 얼마나 낮추는지에 달려 있다. 현재 공개 자료만으로 공급자별 매출 기여와 전환 비용을 정량화할 수는 없다.

## 4. 실행 인터페이스 — 함수·MCP·컴퓨터 사용

| 방식 | 적합한 업무 | 구현·검증 초점 |
|---|---|---|
| 함수/API tool | 구조화된 CRM 조회·재고·승인 등록 | schema·필수 인자·권한·idempotency·응답 상태 |
| MCP | 여러 서비스의 도구·자료 연결 | 서버 신뢰·tool 범위·사용자 identity·진행/입력 처리 |
| Shell·파일 | 자료 분석·코드 변경·문서 생성 | mount·출력 경로·격리·네트워크·비밀정보 경계 |
| Computer use | API가 부족한 웹 업무·화면 작업 | 페이지 접근·인증·UI 변화·행동 후 최종 확인 |

이 표는 구현 선택에 관한 분석이다. API로 안정적으로 처리 가능한 기록 쓰기를 화면 클릭으로 돌리면 성공 판단이 더 복잡해질 수 있다. 반대로 API가 없는 업무에서는 화면 조작이 실제 연결 수단이 된다. 둘의 선택은 데모의 인상보다 완료 검증·유지 비용에 달려 있다.

OpenAI 현행 computer use 문서는 origin·인증 승인 요청을 애플리케이션이 처리하게 한다. 승인 요청 접수는 탐색 성공과 구분된다. 따라서 승인 UI, 중단·재개, 완료 상태 확인은 별도 단계다. [구현 조건](evidence/OAI-AGENTS-20261006-001.md)

## 5. 장시간 실행은 정상 경로보다 복구 경로에서 무너진다

Anthropic은 harness·sandbox·세션을 분리한 내부 구조 변경 뒤 TTFT p50 약 60%, p95 90% 이상 감소를 보고했다. 필요한 때만 실행 환경을 준비하는 구조의 효과이며, 과업 전체가 같은 비율로 빨라졌다는 의미는 아니다. 절대 지연·표본·독립 재현은 공개되지 않았다. [측정 조건](evidence/ANT-RUNTIME-20261006-001.md)

| 실패 장면 | 보존·확인할 것 | 재개 규칙 제안 |
|---|---|---|
| Sandbox 종료 | 파일 snapshot·artifact 위치·현재 단계 | 새 환경 복원 뒤 산출물 검증 |
| Harness 재시작 | durable events·tool 결과·승인 상태 | 마지막 기록에서 이어서 실행 |
| 쓰기 후 timeout | 요청 ID·외부 record ID·수신 상태 | 상태 조회 뒤 필요할 때만 재시도 |
| 권한 회수·인증 만료 | 현재 사용자·tool scope | 읽기/쓰기 재인증, 기존 허용을 무조건 재사용하지 않음 |
| 맥락 압축 오류 | 원 history·근거·미완료 항목 | 관련 사건 재조회, 요약을 사실 원본으로 대체하지 않음 |

복구는 컨테이너를 다시 띄우는 데서 끝나지 않는다. 외부 업무 상태가 이미 바뀌었는지 조회한 뒤 이어가야 한다. 자격증명을 실행 환경 밖에 둬도 정당한 권한을 가진 도구의 오작동까지 막을 수는 없다.

## 6. 멀티 Agent — 분할 가능한 과업과 검증 가능한 산출물

| 실험 관측 | 확인된 규모 | 읽는 방식 |
|---|---|---|
| 병렬 compiler 개발 | 16개 Agent·약 2주·거의 2,000 세션 | 공급자 연구자의 특정 프로젝트 |
| 사용량·비용 | 입력 20억·출력 1억4,000만 tokens; API 약 $20,000 미만 | 설계·검수 노동 포함 총원가 아님 |
| 산출물 | 약 10만 줄 Rust; Linux 6.9 빌드 | 상용 compiler 대체나 유지보수 품질과 별개 |
| 제한 | 일부 GCC 의존·낮은 최적화 효율 | 시험 통과와 완제품 품질 구분 |

[원문·측정 한계](evidence/ANT-TEAMS-20261006-001.md). 이 실험은 Agent를 많이 투입하면 비례해 빨라진다는 근거가 아니다. 작업 경계·공유 상태·충돌 처리·시험 설계가 있어야 병렬 실행의 이점을 얻는다.

실무 적용에서는 독립적인 문서 묶음 분석이나 서로 다른 검증 항목처럼 분리 가능한 과업부터 비교할 수 있다. 여러 Agent가 동일 파일·동일 고객 기록을 수정하면 병합·책임·중복 실행 비용이 커진다. 단일 Agent 기준선을 두고, 병렬화 뒤 수락된 결과당 비용·시간·충돌을 비교하는 것이 합리적이다.

### 6.1 장기 개발 실험: 검증을 추가하면 시간과 비용도 늘어난다

Anthropic의 2026-03-24 실험은 같은 Opus 4.5와 게임 제작 요청으로 단일 Agent와 planner·generator·evaluator 구성을 비교했다. 단일 실행은 20분·$9, 전체 하네스는 6시간·$200였다. 단일 결과의 플레이 기능은 작동하지 않았고 전체 하네스는 핵심 기능을 구현했지만 오류가 남았다. [공식 실험·비교 한계](evidence/ANT-HARNESS-20261007-001.md)

| 비교 항목 | 관측 | 비용을 해석할 때 남는 문제 |
|---|---|---|
| 단일 실행 | 빠르고 저렴했으나 핵심 기능 실패 | 실패 결과에 지불한 비용 |
| 생성·평가 반복 | 기능 검증과 수정에 추가 시간·호출 사용 | 사람이 절약한 QA 시간은 미측정 |
| planner가 범위를 확대 | 전체 하네스가 더 많은 기능 구현 | 동일 산출물 범위의 통제 비교가 아님 |
| 신모델에 맞춘 단순화 | 후속 Opus 4.6 구성에서 sprint 분해 제거 | 다른 과업 결과를 비용 절감률로 비교 불가 |

생성·평가 호출을 늘려 검증 가능한 결과를 얻었지만 비용도 증가했다. Agent 수를 늘린 효과를 비용 절감으로 자동 환산할 수는 없다. 고객이 원하는 핵심 기능을 수락 기준으로 고정하지 않으면 더 많은 기능을 만든 결과가 더 나은 경제성처럼 보일 수 있다.

개발 Agent 시장에서 평가 도구·실행 환경·로그가 모델 옆에 붙는 이유도 여기서 드러난다. 코드 생성만 판매하면 오류 수정 비용을 고객이 떠안는다. 실행·시험·수정을 묶으면 공급자가 더 많은 호출과 연산을 판매하면서 고객의 검수 부담을 줄일 수 있다. 그 교환이 유리한지는 수락한 기능의 수, 사람 수정 시간과 유지보수 비용으로 판단해야 한다. 단일 공급자 실험을 전체 개발 생산성이나 인력 대체율로 확대하지 않는다.

## 7. 성공·일관성·비용을 함께 평가

| 평가 항목 | 직접 확인할 대상 | 피할 해석 |
|---|---|---|
| 업무 성공 | 실제 DB·artifact·승인 완료 | ‘완료했다’라는 발화만 채점 |
| 부작용 | 다른 기록·권한·데이터 변경 | 목표 결과만 보고 손상을 누락 |
| 반복 일관성 | 동일 과업 다회 trial | 최고 성공 사례를 평균으로 제시 |
| 복구 | timeout·restart·인증 실패 과업 | 정상 경로 성공을 복구 보장으로 사용 |
| 경제성 | tokens·tools·compute·재시도·검수 | 단일 token 가격으로 총원가 추정 |

[Agent eval 원문](evidence/ANT-EVALS-20261006-001.md)은 pass@k와 pass^k를 구분한다. **가상 예시**로 매회 성공률 90%이고 독립이면, 3회 중 한 번 이상 성공은 99.9%, 3회 모두 성공은 72.9%다. 실제로는 실패가 동일 데이터·권한·도구에 상관될 수 있어 이 산식을 그대로 적용할 수 없다.

1. 실제 실패를 포함한 과업과 최종 상태의 정답을 정의한다.
2. 코드 검증으로 상태·부작용을 확인하고 모호한 품질은 전문가 기준을 추가한다.
3. 모델·harness·tool 버전과 반복 횟수를 함께 기록한다.
4. 변경 전후 성공·복구·완료시간·수락당 비용을 비교한다.

### 7.1 외부 Agent가 기업의 분석 Agent를 호출하기 시작했다

Databricks는 2026-09-22 Genie One MCP의 GA를 발표했다. 외부 Agent가 질문을 보내면 Genie가 기업 맥락과 데이터 권한을 적용해 분석하고 결과를 반환한다. 이 구조는 범용 실행 Agent와 데이터 전문 Agent를 연결한다. [제품·현행 API](evidence/DB-MCP-20261007-001.md)

| 실행 단계 | 범용 Agent | 데이터 전문 Agent·플랫폼 |
|---|---|---|
| 사용자 요청 | 보고서·개발·고객 대응 과업을 해석 | 분석 질문을 접수 |
| 데이터 조사 | 필요한 업무 질문을 전달 | 의미·권한을 적용해 검색·SQL 실행 |
| 진행 확인 | 요청 ID로 완료 상태를 조회 | 진행·실패·결과를 반환 |
| 후속 작업 | 문서 생성·추가 판단·허용된 도구 실행 | 분석 근거와 결과 제공 |

MCP 연결이 업무 완료까지 증명하지는 않는다. 분석 결과를 보고 이메일을 보내거나 CRM을 수정하는 책임은 호출 측에 남는다. 결과의 기간·정의·출처를 확인한 뒤 후속 쓰기의 승인과 수신 상태를 검증해야 한다. 분석 성공을 거래 성공으로 자동 승격하면 잘못된 수치가 실제 업무 변경으로 이어질 수 있다.

시장에서는 업무 접점과 공통 지식 제공자가 다른 회사일 수 있다. 사용자는 익숙한 Agent 화면을 유지하고 데이터 플랫폼은 분석·권한·맥락의 경로를 확보한다. 범용 Agent 공급자의 모델을 바꿔도 같은 지식 서비스를 호출할 수 있다는 선택권이 생긴다. 다만 API 형식·identity·분석 이력·요금은 플랫폼에 남는다. 연결의 표준화가 모든 공급자 의존을 없애지는 않는다.

## 8. 실행 우선순위

2026년에는 실행 인프라가 상품이 됐다. 기업은 장기간 실행 기능 위에 업무 수락과 실패 복구 기준을 붙여야 한다. 공급자가 agent loop의 어디까지 맡는지, 상태가 어디 남는지, 외부 쓰기를 어떻게 검증하는지가 비교 기준이다.

- **읽기·분석**: 명확한 출처와 검증 가능한 산출물부터 managed/SDK 기준선을 만든다.
- **제한된 쓰기**: 허용 tool·대상·업무 ID·승인·수신 상태를 연결한다.
- **장시간·병렬 작업**: checkpoint·충돌·복구·compute 비용이 추가되는 효과를 측정한다.
- **확장 판단**: 관측된 성공률과 수락당 비용으로 정하고, 데모 시간·Agent 수로 결정하지 않는다.

위 우선순위는 적용 가설이다. 공개 원문만 확인했으며 실제 기업 시스템의 운영 성능은 측정하지 않았다. 지식·권한·메모리 설계는 [I-4](I-4_knowledge_data_memory.md), 과업당 경제성은 [I-2](I-2_models_cost.md)에 연결한다.
