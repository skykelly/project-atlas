# I-4. 기업 지식·데이터·메모리

[주제 목차](README.md) · [Agent 실행](I-3_agents_execution.md) · [변경 이력](LOG.md)

조사 범위 **2026-01-01~2026-10-06**, 현행 문서 확인일 **10-06**. 제품 발표·현재 문서·기업 내부 벤치마크를 구분했다. 적용 예시는 설계 설명이며 실제 고객 성과가 아니다.

## 1. 기업 AI는 문서보다 업무 정의에서 먼저 틀린다

‘이번 달 매출이 왜 줄었나’라는 질문은 문서 검색만으로 풀리지 않는다. 매출 정의, 기간, 환불 처리, 비교 기준, 사용자가 볼 수 있는 사업 범위가 먼저 맞아야 한다. 같은 단어도 재무·영업·운영 시스템에서 다른 대상을 가리킨다.

2026년 Databricks·Snowflake 발표와 Glean 문서는 검색 결과에 업무 의미와 권한을 결합한다. 검색, 의미 모델, 권한, 세션, 메모리는 각각 다른 실패를 막는다. 한 계층을 도입해도 나머지 문제는 남는다.

| 계층 | 해결하는 질문 | 예시 | 주요 실패 |
|---|---|---|---|
| 원 데이터 | 실제로 어떤 일이 있었나? | 주문·환불·계약 원본 | 누락·지연·오류 |
| 검색·RAG | 필요한 근거는 어디 있나? | 정책 조항·관련 ticket 검색 | 오래된 자료·무관한 문서 |
| Semantic layer | 수치를 어떤 정의로 계산하나? | 순매출·활성고객 정의 | 부서별 지표 충돌 |
| Ontology·graph | 개념·대상·관계는 어떻게 연결되나? | 고객·계약·상품·소유자 | 잘못된 관계·범위 |
| 권한·공개 범위 | 누가 읽고 누가 결과를 볼 수 있나? | 개인 대화와 공동 채널 | 공유 응답으로 정보 노출 |
| Session·memory | 지금 진행과 미래 기억은 무엇인가? | 이번 분석·승인한 선호 | 잘못 기억·삭제 누락 |

이 표는 개념을 구분하기 위한 분석이다. RAG는 검색 근거를 생성에 넣는 방식이고, GraphRAG는 관계를 이용한 검색·맥락 구성 방식이다. 그래프 구축만으로 업무 정의 합의와 접근 권한이 따라오지는 않는다.

## 3. 공급자별 접근 비교

| 접근 | 대표적으로 잘 다루는 맥락 | 실행·통제 연결 | 한계·판단 조건 |
|---|---|---|---|
| Databricks Genie Ontology | 인증된 의미·자산에서 추론한 업무 지식 | source authority·UC 권한·Genie 경험 | 추론 지식을 인증 정의와 구분; Public Preview |
| Snowflake Semantic View·Cortex | 구조 데이터의 지표와 비구조 문서 | Analyst SQL·Search·configured tools | semantic view가 모든 개념 관계를 대체하지 않음 |
| Glean knowledge profiles | 여러 업무 자료의 검색 범위·공유 맥락 | 요청자·공유 corpus 정체성 구분 | 개인 답변을 공동 채널로 옮기는 검증 필요 |
| Stardog 방향 | ontology·관계·정책·지식 stewardship | 실패 질문을 의미 모델 개선 신호로 활용 | 해당 글은 비전, 정량 ROI·별도 GA 확인 아님 |
| Databricks managed memory | 사용자·과업에서 장기 보존할 사실·결정 | actor별 저장·검색, session provenance | Beta; 기억을 공인 기업 지식으로 자동 승격하지 않음 |

다섯 접근은 해결하는 실패가 다르다. 지표 정의가 충돌하는 조직과 공유 문서 권한이 새는 조직은 다른 계층부터 고쳐야 한다. 기존 data warehouse·업무 connector·사용자 identity와 맞는 계층을 선택하고, 부족한 기능을 구체적으로 확인해야 한다.

## 4. Ontology·semantic layer가 필요한 장면

**설명 예시**로 ‘활성 고객 수’를 영업은 최근 상담한 고객, 제품팀은 실제 사용한 고객, 재무는 유료 고객으로 볼 수 있다. 검색 결과가 모두 사실이어도 어떤 정의를 사용할지 결정하지 않으면 답변은 충돌한다. 업무 의미를 데이터·팀·기간에 연결하는 계층은 이 충돌을 드러내고 질문에 맞는 정의를 고르는 데 도움을 준다.

| 필요한 지식 | 기록할 내용 | 운영 책임 |
|---|---|---|
| 지표 정의 | 분모·분자·기간·중복·제외 규칙 | 해당 지표 owner |
| 권위 있는 출처 | 승인된 report·metric·agent | 인증·변경 승인 |
| 개념 관계 | 고객·계약·계좌·상품의 연결 | 업무 steward·데이터 owner |
| 시점·버전 | 유효 시작·종료·변경 이력 | 갱신·폐기 관리 |
| 불확실성 | 정의 충돌·접근 불가·누락 | 답변 보류·확인 경로 |

Databricks 현행 문서는 modeled semantics와 inferred snippets를 나눈다. 추론 지식은 자산 출처·사용·신선도에 따른 authority와 권한을 반영한다. 사용 빈도가 높아도 모든 업무의 공인 정의가 되지는 않는다. 핵심 지표의 owner와 인증 여부를 함께 확인해야 한다. [제품 조건](evidence/DB-ONTOLOGY-20261006-001.md)

Snowflake는 metric semantics를 활용해 SQL 분석과 문서 검색을 한 workflow에 연결한다. 공급자 표현인 ‘days to minutes’에는 표본·측정 기준이 없어 모든 기업의 구축 시간 절감률로 사용하지 않는다. Simon AI 등의 고객 인용도 방향을 보여 주는 자료로 다룬다. [원문·한계](evidence/SNOW-SEMANTIC-20261006-001.md)

## 5. 공급자 벤치마크에서 제품 효과를 분리한다

| Databricks 2026년 6월 내부 비교 | 발표 값 | 측정 조건 |
|---|---:|---|
| Genie 첫 시도 정확도 | 84.5% | enterprise data-analysis 28-question suite |
| 가장 강한 general-purpose coding agent | 52.4% | 경쟁 agent 이름 익명 |
| 정확도 차이 | 32.1%p | 단순 차감, 독립 검증 아님 |
| 속도 | 약 2배 빠름 | 가장 강한 비교 agent 대비 공급자 보고 |

[원문·조건](evidence/DB-ONTOLOGY-20261006-001.md). 이는 기업 데이터의 맥락을 갖춘 시스템이 일반 coding agent보다 좋은 결과를 낼 수 있다는 공급자 근거다. Ontology 하나만 바꾼 통제 실험이 아니므로 차이 전체를 Ontology의 효과로 해석할 수 없다. 질문 수가 작고 반복·집계 세부가 없어 정확도를 성공 건수로 역산하거나 한국어 질문에 적용해서도 안 된다.

도입 검증에서는 같은 데이터·권한·질문·정답 정의를 고정하고 검색만 사용하는 기준선과 비교한다. 올바른 SQL이라도 잘못된 매출 정의를 사용하면 실패로 채점해야 한다. 지식 추출·인증·운영에 쓰는 시간과 query·index 비용도 함께 측정해야 비교가 완성된다.

## 6. 권한은 검색 정체성과 응답의 청중까지 포함한다

Glean의 현행 문서에는 web·개인 Slack 응답과 채널 전체 가시 응답의 검색 맥락이 다르게 설명되어 있다. 개인 요청자가 읽을 수 있는 자료를 그대로 공동 답변에 포함하면 다른 수신자에게 정보가 드러날 수 있기 때문이다. 공유 Agent 권한만으로 자료·응답의 접근 문제가 해결되지는 않는다.

| 상황 | 검색·공개 기준 | 실무 확인 항목 |
|---|---|---|
| 개인 web·개인 가시 Slack | 요청자 개인 권한 | 사용자 매핑·권한 회수 |
| 채널 전체 응답 | broad-access corpus | 공유 가능한 원문·현재 채널 범위 |
| Public data auto-agent | admin knowledge profile | connector·workspace·group 범위 |
| API로 agent 호출 | Agent-scoped token과 실행 설정 | 호출 권한과 데이터 권한의 분리 |

[현행 조건](evidence/GLEAN-ACCESS-20261006-001.md). 여기의 Public은 인터넷 공개가 아니다. broad-access 모델도 모든 구성원의 개별 문서 권한을 교집합으로 계산한다는 뜻은 아니다. 선택한 profile이 허용하는 corpus를 기준으로 응답한다.

권한 검증은 원문·인용·요약·캐시·메모리 전체를 훑어야 한다. 퇴사자 권한을 회수해도 과거 공유 요약이나 장기 기억에 정보가 남을 수 있다. 제품 보장으로 확인된 내용은 아니다. 조직이 직접 시험해야 할 항목이다.

## 7. 세션·메모리·기업 지식을 구분하는 설계

| 저장 대상 | 보존 목적 | 삭제·신뢰 기준 제안 |
|---|---|---|
| Session | 지금 과업을 재개할 history·상태 | 과업 수명·감사·재개 정책 |
| 장기 memory | 사용자 선호·과거 결정·지속 과업 | subject identity·출처·동의·만료·별도 삭제 |
| 기업 knowledge | 조직의 승인된 사실·정의 | source owner·권한·인증·버전 |

Databricks는 세션에서 가치 있는 사실을 추려 memory에 기록하는 연결을 설명한다. **세션 삭제는 별도 memory 삭제가 아니다.** memory의 actor_id는 검증된 identity를 사용해 애플리케이션이 정하도록 안내한다. 모델이 기억의 소유자를 자유롭게 고르게 하면 사용자 간 정보를 섞을 위험이 있다. [원문](evidence/DB-MEMORY-20261006-001.md)

현행 overview는 semantic search라는 표현을 쓰지만 상세 retrieval 문서는 BM25 ranking을 명시한다. 이번 조사에서는 이를 vector memory라고 단정하지 않는다. 같은 ‘memory’ 명칭도 저장 구조·검색 방식·권한·삭제 정책이 다르므로 실제 API 조건을 읽어야 한다. Beta 중 memory 자체 추가 요금과 Lakebase 원가도 구분해야 한다.

사용자의 ‘다음 보고서는 짧게’ 요청은 개인 선호로 저장할 수 있다. 회사 매출 집계 규칙은 바꿀 수 없다. 장기 기억을 기업 knowledge로 승격하려면 owner 검토, 원문 근거, 유효 기간을 거쳐야 한다.

## 8. 실행 가능한 지식 운영 패턴

Stardog은 답할 수 없는 질문을 지식의 개념·관계·정책 공백을 드러내는 신호로 다루고 knowledge steward의 검토를 제안한다. 이 글은 공급자의 운영 비전이며 자동으로 지식 모델이 완성되거나 특정 ROI가 검증되었다는 근거는 아니다. [방향·한계](evidence/STAR-CONTEXT-20261006-001.md)

1. **업무 질문을 고정한다.** 재무 지표·정책 예외·계약 위험 등 자주 쓰는 질문과 정답 정의를 정한다.
2. **근거와 의미를 연결한다.** 원 데이터·metric·문서·관계·owner·유효 시점을 함께 관리한다.
3. **개인·공유 경로를 나눈다.** retrieval identity와 응답 청중을 고정하고 누출 시험을 수행한다.
4. **실패 이유를 분류한다.** 검색 누락·정의 충돌·권한 차단·원 데이터 오류·기억 오류를 구분한다.
5. **개선 후 다시 평가한다.** 새 지식이 정답률을 높이면서 기존 과업·권한을 훼손하지 않는지 확인한다.

| 측정 축 | 실질적인 지표 | 반드시 함께 기록할 조건 |
|---|---|---|
| 답변 품질 | 정확한 정의·근거·계산 비율 | 질문 집합·정답 owner·기간 |
| 근거 신뢰 | 유효 출처·충돌 해결·출처 추적 | 문서·metric 버전 |
| 접근 통제 | 허용/금지 질문의 정상 처리 | 사용자·채널·tool identity |
| 갱신 | 변경에서 검색·응답 반영까지 지연 | connector·index·cache 경로 |
| 기억 품질 | 정확한 subject·결정·삭제 반영 | session과 memory 수명 |
| 운영비 | 수락된 답변당 전체 비용 | tokens·index·query·steward 노동 |

## 9. 적용 우선순위

시장은 검색에 업무 의미·권한·지속 기억을 결합하고 있다. Data platform은 지표와 실행을, 업무 검색 플랫폼은 자료 접근과 공유 맥락을, semantic 전문 사업자는 지식 모델과 검토 운영을 맡는다. 이들은 서로 다른 장애물을 제거한다.

- 지표가 충돌하면 semantic definition과 owner부터 정한다.
- 자료가 흩어져 있으면 검색·connector·권한·신선도를 먼저 검증한다.
- 관계 판단이 필요하면 작은 업무 ontology를 정답 질문과 함께 평가한다.
- 반복 대화가 필요하면 memory의 identity·출처·수명·삭제를 분리한다.
- 업무 쓰기로 연결할 때는 [I-3](I-3_agents_execution.md)의 최종 상태·중복 방지·복구를 함께 설계한다.

이 우선순위는 적용 제안이다. 공개 제품 문서만으로 데이터 품질·한국어 성능·개별 계약·도입 ROI를 확정하지 않았다. 완성도는 연결 문서 수로 재지 않는다. 합의한 의미와 허용된 근거로 답하고, 잘못된 기억·접근·변경을 추적할 수 있어야 한다.
