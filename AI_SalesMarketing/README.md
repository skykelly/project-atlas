## 어떻게 읽고 갱신하는가

카테고리 문서에서 연구 질문·사례 목록·종합을 읽고, 연결된 cases의 개별 문서에서 적용 내용·성과·출처·검증 상태를 확인한다. 같은 사례는 한 번만 작성하고 여러 카테고리에서 연결한다.

수정 기준은 **Markdown**이다. 사례 사실·근거는 해당 사례 문서, 비교·시사점은 카테고리 문서, 변경·보류·다음 조사는 LOG.md에 둔다. 별도 출처 DB나 편집용 JSON을 함께 관리하지 않는다.

## 사례 큐레이션 상태

각 사례의 `curation_status`는 위키 종합에서의 쓰임을 나타내고, `review_status`와 `source_checked_at`은 원문 검증 여부를 나타낸다. 큐레이션과 사실 검증을 같은 의미로 사용하지 않는다.

| 상태 | 건수 | 판정 기준 |
| --- | ---: | --- |
| 채택 | 22 | 원문과 주요 주장·수치를 확인했으며 현재 1-1~2-2 종합의 근거로 사용 |
| 보조 근거 | 32 | 실제 적용과 성과 또는 운영 방식이 있으나 원문 재검토 전에는 핵심 근거로 사용하지 않음 |
| 보류 | 37 | 관련성은 있으나 출처·AI 기여·측정 조건 중 하나 이상을 추가 확인해야 함 |
| 제외 | 26 | 실제 기업의 AI 영업·마케팅 적용 및 성과 사례로 보기 어려워 현재 종합에서 제외 |

`제외`는 원본 삭제를 뜻하지 않는다. seed 추적을 위해 문서를 보존하며, 더 강한 원문이 확인되면 다시 판정할 수 있다.

## 빠른 주간 갱신 방식

주간 작업은 기존 종합을 매번 다시 쓰지 않고 **신규 근거의 증분 처리**만 수행한다.

1. 최근 14일 자료를 검색하고 기존 URL과 중복된 후보를 제거한다.
2. `실명 기업 + 실제 적용 + 실행 방식 또는 사업 성과`가 있는 후보만 원문 검토 대상으로 남긴다.
3. 채택 가능성이 높은 후보부터 원문을 열고, 출처·지표·측정 조건을 사례 문서 한 곳에 기록한다.
4. 새 근거가 기존 결론을 바꾸거나 강화할 때만 카테고리 종합을 수정한다. 결론 변화가 없으면 사례와 LOG만 갱신한다.
5. 보류·제외 자료는 다음 주에 반복 검색하지 않고, 새 원문이나 수치가 발견될 때만 다시 검토한다.

주간 실행은 신규 후보 선별과 사례 반영에 집중한다. 카테고리 전체의 비교·문장 재작성과 큐레이션 재평가는 월간 또는 중요한 근거가 나온 시점에 수행한다.

## 새 사례의 최소 형식

cases 아래에 고유 ID.md를 만든다. 문서 상단에는 id, category, company, tags, review_status, source_checked_at, updated_at을 기록한다. topic과 ai_mode는 근거가 있을 때만 넣는다. seed에서 가져온 문서만 seed_added_date와 legacy_verified를 유지한다.

본문은 요약 → 적용 내용 → 성과와 측정 조건 → 출처와 검증 → 한계와 다음 확인 순서로 작성한다. 출처별 URL·게시일·확인일과 주장별 근거 위치를 같은 문서에 기록한다. 원문을 읽지 않았다면 source_checked_at은 null로 둔다.

지표는 가능하면 값·단위·기간·표본·비교 대상·근거를 함께 적고, 실제 성과·목표·예측·자기 보고를 구분한다. LG 적용 아이디어는 가설로 표시한다.
